# 晚枫家政 · 数仓分层设计与维度建模

> 本文档是「晚枫家政离线数仓」项目的设计说明书，与代码逐字对应。
> 配套实现见 `docker-compose.yml`、`hive/01~04_*.sql`、`airflow/dags/wanfeng_etl.py`、`generate_data.py`。

---

## 1. 项目背景与目标

晚枫家政已有业务系统（Vue3 + Express + MySQL），产生订单、评价、用户、师傅等业务数据。
这些数据分散在业务库中，且存在大量「脏数据」（自由文本地址、混合日期格式、JSON 字段等），
无法直接支撑经营分析。

**目标**：搭建一套 Hadoop + Hive 离线数仓，把业务数据加工成经营分析报表，形成完整数据链路：

```
业务系统(MySQL) → 造数导出 CSV → HDFS → Hive 数仓(ODS/DWD/DWS/ADS) → Airflow 每日调度 → ECharts 数据大屏
```

## 2. 总体架构

## 3. 分层设计

### 3.1 ODS 贴源层（Operational Data Store）

**定位**：原样落地业务数据，不做任何加工，保证「可回溯、可重算」。

**设计原则**：
- 所有字段统一 `STRING`，避免加载时因类型不匹配丢数据；
- 存储用 `TEXTFILE`（贴源、无压缩开销，保留原始形态）；
- 字段名保留业务语义，仅处理 SQL 保留字（如评价表的 `date` 列改名 `dt`）；
- 显式保留脏数据（空串、`\N`、混合日期格式、非法 JSON），供下游 DWD 清洗。

**表清单（7 张）**：

| 表 | 类别 | 说明 | 脏数据 |
|---|---|---|---|
| ods_bookings | 事实 | 订单（100 万） | 混合日期 / 自由地址 / staff_id、price 空 |
| ods_reviews | 事实 | 评价（20 万） | 混合日期 / stars 越界 0、6 |
| ods_users | 维度 | 用户（10 万） | 自由地址 / preferences JSON |
| ods_staff | 维度 | 师傅（30） | tags JSON（5% 非法） |
| ods_services | 维度 | 服务（6） | 干净 |
| ods_dim_date | 维度 | 时间（3 年 1096 行） | 干净 |
| ods_dim_region | 维度 | 区域（32） | 干净 |

### 3.2 DWD 明细层（Data Warehouse Detail）

**定位**：对 ODS 做清洗、去重、标准化、字段转型，形成「干净、可复用」的明细事实与维度。

**设计原则**：
- 维度表与事实表分离，构建星型模型；
- 存储改 `ORC`（列式压缩，实测 ODS 200MB → DWD 39MB）；
- 字段完成类型转型（STRING → DATE/INT/DECIMAL/TIMESTAMP）；
- 统一数据口径（见 §6）。

**核心清洗逻辑**：

| 清洗点 | 脏数据样例 | 处理方式 |
|---|---|---|
| 日期统一 | `2025/03/31`、`03-15-2025`、`20250315`、`2023年2月14日`、空串、`\N` | 正则匹配多格式 → `unix_timestamp` 解析为 DATE；空/乱码 → NULL |
| 区域解析 | address 自由文本 `广东省广州市天河区…` | `LEFT JOIN dim_region ON address LIKE '%区名%'` 提取 region_id |
| 越界值 | stars 出现 0 / 6 | `CASE WHEN stars BETWEEN 1 AND 5`，否则 NULL |
| 空值 | staff_id / price 为空串或 `\N` | `CAST('' AS INT/DECIMAL)` → NULL |
| 去重 | 主键重复 | `ROW_NUMBER() OVER(PARTITION BY id)` 取 rn=1 |

清洗效果（100 万订单实测）：日期解析成功率 ≈ **96%**、区域覆盖率 ≈ **91%**（缺失地址正确置 NULL，不污染汇总）。

**表清单（7 张）**：维度表 `dim_date / dim_region / dim_service / dim_staff / dim_user`，
事实表 `dwd_bookings / dwd_reviews`（字段见 §5）。

### 3.3 DWS 汇总层（Data Warehouse Summary）

**定位**：按天 / 按主题对 DWD 做轻度汇总，屏蔽明细复杂度，向上层提供统一指标。

**指标口径（关键，全链路统一）**：

| 指标 | 口径 |
|---|---|
| order_cnt | 总订单量（含取消） |
| valid_cnt | 有效订单量（`status = 'completed'`） |
| cancel_cnt | 取消订单量（`status = 'cancelled'`） |
| order_amt | 营收 = `completed` 订单 price 合计（NULL 忽略） |
| avg_price | 客单价 = order_amt / valid_cnt |

**表清单（4 张）**：

| 表 | 粒度 | 用途 |
|---|---|---|
| dws_order_daily | 日 | 日订单量/有效量/取消量/营收/客单价 |
| dws_service_daily | 日 × 服务 | 各服务每日订单与营收 |
| dws_region_daily | 日 × 区域 | 各区域每日订单与营收 |
| dws_staff_stats | 师傅 | 师傅累计业绩（订单/营收/均分） |

> 实现要点：`dws_staff_stats` 将订单事实与评价事实**先各自按 staff_id 聚合，再关联**，
> 避免两个事实表直接 join 造成的扇出放大（笛卡尔积）。

### 3.4 ADS 应用层（Application Data Store）

**定位**：直接面向报表 / 大屏，产出最终指标，接口稳定、口径固化。

**表清单（2 张）**：

| 表 | 用途 | 大屏消费 |
|---|---|---|
| ads_staff_performance | 师傅业绩榜（按营收排名 + 均分） | 师傅业绩榜 |
| ads_monthly_report | 月度经营报表（36 个月 + 订单量环比） | 月度订单/营收趋势 |

- `ads_staff_performance` 用 `ROW_NUMBER() OVER(ORDER BY order_amt DESC)` 生成排名；
- `ads_monthly_report` 用 `LAG(order_cnt) OVER(ORDER BY ym)` 计算环比 `(本月-上月)/上月`。

## 4. 维度建模（星型模型）

### 4.1 事实表 vs 维度表

| 类型 | 表 | 量级 | 特征 |
|---|---|---|---|
| 事实表 | dwd_bookings | 100 万 | 量大、不断增长、含可加性度量（price） |
| 事实表 | dwd_reviews | 20 万 | 含 stars 度量 |
| 维度表 | dim_date | 1096 | 小、相对稳定、描述属性 |
| 维度表 | dim_region | 32 | 小 |
| 维度表 | dim_service | 6 | 小 |
| 维度表 | dim_staff | 30 | 小 |
| 维度表 | dim_user | 10 万 | 中型，描述用户画像 |

### 4.2 星型模型结构

```
                        ┌──────────────┐
                        │  dim_date    │  时间维度（服务日期/评价日期）
                        │  (date/dow…) │
                        └──────▲───────┘
                               │ dt
        ┌──────────────┐      ┌┴─────────────────────────┐
        │ dim_region   │◄─────│  dwd_bookings (事实表)      │
        │ (region_id)  │ r_id │  booking_id, service_date  │
        └──────────────┘      │  region_id, staff_id,      │
        ┌──────────────┐      │  status, price, …          │
        │ dim_staff    │◄─────│                            │
        │ (staff_id)   │ s_id │                            │
        └──────────────┘      └────────────────────────────┘
        ┌──────────────┐      ┌────────────────────────────┐
        │ dim_service  │      │  dwd_reviews (事实表)        │
        │ (service_id) │      │  review_id, staff_id,       │
        └──────────────┘      │  review_date, stars, …      │
                              └────────────────────────────┘
```

**关联关系**（外键 / 退化维度）：
- `dwd_bookings.service_date → dim_date.dt`（通过日期关联时间维度）
- `dwd_bookings.region_id → dim_region.region_id`
- `dwd_bookings.staff_id → dim_staff.staff_id`
- `dwd_reviews.staff_id → dim_staff.staff_id`、`dwd_reviews.review_date → dim_date.dt`
- **退化维度**：订单事实表冗余了 `service`（服务名）、`user_name / user_phone`（用户信息），
  未单独以 service_id / user_id 外键关联，属于数仓中常见的「退化维度」处理（避免过深的 join，简化下游查询）。

### 4.3 粒度与一致性

- 事实表粒度：一张订单一行（`dwd_bookings`）、一条评价一行（`dwd_reviews`）；
- 维度表粒度：一个自然键一行（一天 / 一区 / 一服务 / 一师傅 / 一用户）；
- 维度表采用**全量覆盖（SCD Type 1）**：每次 ETL `INSERT OVERWRITE`，不保留历史版本。
  对本项目（快照式经营分析）足够，且实现简单、无缓慢变化维的存储成本。

## 6. 关键设计决策

1. **存储格式分层差异化**：ODS 用 `TEXTFILE`（贴源、可读性、无转换），DWD/DWS/ADS 用 `ORC`（列式压缩，
   实测 ODS 200MB → DWD 39MB，压缩约 5 倍，且支持谓词下推、列裁剪）。
2. **未做分区/分桶**：当前为单机演示环境，数据量百万级，全表扫描即可在秒级完成；
   若生产扩到亿级，可在 `dwd_bookings` 按 `service_date` 做日期分区（`PARTITIONED BY(dt STRING)`）。
3. **脏数据「可追溯」策略**：ODS 层绝不丢弃脏数据，脏数据在 DWD 层统一置 NULL，
   下游 DWS 汇总时以 `WHERE service_date IS NOT NULL` 过滤，保证「清洗逻辑可回放、口径可解释」。
4. **指标口径前移**：`order_amt / valid_cnt / avg_price` 等口径在 DWS 层一次算好并固化，
   ADS 层只做排名与环比，避免口径散落、重复计算。
5. **扇出控制**：多事实表关联（订单×评价）时先各自聚合再 join，杜绝笛卡尔积。
6. **调度幂等**：每层 `INSERT OVERWRITE`（先删后写），DAG 可重复触发而不产生重复数据；
   失败重试（`retries=1`）不会破坏结果。

## 7. 数据流与调度

### 7.1 ETL 依赖链（Airflow DAG `wanfeng_etl`）

```
01_ods ──► 02_dwd ──► 03_dws ──► 04_ads
```

- 调度频率：`@daily`（每天 00:00）；
- 执行方式：pyhive 连接 HiveServer2（`auth=NONE`，SASL PLAIN）逐层执行 SQL；
- 数据落地：全部写 `hdfs://namenode:8020/warehouse/`。

### 7.2 各层数据量（100 万订单实测）

| 层 | 存储 | 数据量 |
|---|---|---|
| ODS | TEXTFILE | ~200 MB |
| DWD | ORC | ~39 MB（压缩约 5×） |
| DWS | ORC | ~192 KB |
| ADS | ORC | ~3.3 KB |

> DWD 相比 ODS 明显缩小，除了 ORC 压缩，还因为字段由 STRING 转为定长数值/日期类型，存储更紧凑。

## 8. 与业务系统 / 大屏的衔接

- **抽取**：`generate_data.py` 按业务 schema 生成 CSV，模拟「MySQL 导出」，`LOAD DATA` 进 ODS。
  真实生产环境此处可替换为 DataX / Sqoop 做增量抽取，表结构与清洗逻辑不变。
- **消费**：数据大屏的 ECharts 组件直接查询 ADS 层：
  - 月度趋势 → `SELECT * FROM wanfeng_ads.ads_monthly_report ORDER BY ym;`
  - 师傅业绩 → `SELECT * FROM wanfeng_ads.ads_staff_performance ORDER BY rnk;`
- **闭环**：业务系统产生数据 → 数仓加工 → 大屏呈现，形成「数据产生 → 数据加工 → 数据应用」的完整链路。
